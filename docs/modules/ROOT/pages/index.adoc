= Modulith
:description: FF Logistic as one Spring Modulith application.

One process, `logistics-app`, runs every business area. The areas are the domain cores from ff-logistic-shared; this application wires them together in-process:

* a question to another area is a method call through its port,
* an event is a Spring Modulith event, recorded in the same transaction and delivered to listeners in the same JVM,
* Spring Modulith verifies that no area reaches into another except through its ports.

[cols="1,3",options="header"]
|===
| Path | What

| `logistics-app` | The application: every domain core, the chassis (ff-base-app), the `flows` module that wires the areas together, one `ModularityTest`
| `deploy/apps/logistics-app` | Its values for the runtime's chart; the switch deploys it when `active: modulith`
|===

[[flows]]
== The flows, in-process

The `flows` module exists only here: it connects one area's API to another's, which no core may do itself (decision 2). Flow 2 (S4): `DeliveriesToWarehouses` hears transportation's `ShipmentDelivered` after the commit, on a thread of its own, and calls warehousing's `InboundArrivals.open`. The event publication registry stores the event with the delivery, in this process's outbox (schema `modulith`, ff-base-events), and delivers it again if the listener fails. `ModularityTest` checks that `flows` uses both areas through their APIs only.

Flows 1 and 3 (S5), between routing and transportation:

* *Flow 1, a question*: `RoadDistancesForTransportation` fills transportation's port `DistanceLookup` with routing's `RoadDistances`. A method call, so routing cannot be "down" while transportation runs (xref:ff-logistic::architecture.adoc#flow-1[on each side]).
* *Flow 3, an event*: `StopsToShipments` hears routing's `RouteStopCompleted` after the commit, on a thread of its own, and calls transportation's `ShipmentDeliveries.deliver`. The delivery's own `ShipmentDelivered` then runs flow 2: one completed stop, three areas (xref:ff-logistic::architecture.adoc#flow-3[on each side]).

[source,bash]
----
./build.sh                                              # after base and shared are installed
docker build -t ghcr.io/ffetih/ff-logistic-modulith/logistics-app:local logistics-app
k3d image import ghcr.io/ffetih/ff-logistic-modulith/logistics-app:local -c ff-logistic
----

From the IDE, against the cluster's PostgreSQL and identity service: run `LogisticsApplication` with the `local` profile to call it without a token (`X-Tenant-Id` header). The services side does the same work over the network: xref:services::index.adoc[Services].
